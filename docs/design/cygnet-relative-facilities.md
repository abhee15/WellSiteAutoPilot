# CygNet relative facilities and hierarchy (probe J1/J2)

Status: **partial probe.** Questions 1-4 are answered with evidence. Question 5 (adapter prototype with relationMap,
simulator support, tests and a discovery hint option) was **not started**. Nothing was written to CygNet; all calls were reads.

## 1. How relative facility definitions work

Evidence: ForeSite `CygNetRelativeFacilityHelper.cs`, `POP.Settings\RelativeFacilityMapping.cs`, `CygNet.API.Facilities.dll`
(reflection and IL via ildasm), live probe `poc\cygnet-relative-probe`.

- A definition set is a `RelativeFacilityDefinitionSets` (CygNet.API.Facilities.Relative). It holds one or more
  `RelativeFacilityDefinitions` (a "FacilityDefinitions" XML document) keyed to FAC services (`GetDefinitionSetByFacilityService("SITE.FAC")`).
- XML shape (generated by the API): `<FacilityDefinitions FacilityLinkAttribute="facility_attr22" RelativePathFormat="SIMPLE" Name=".." Services="..">`
  with `<FacilityDefinition Name Filter>` children, each holding `<ReferencePaths><ReferencePath Name="Target">path</ReferencePath>`.
  - `FacilityLinkAttribute` is the facility attribute that holds the parent link (on CYG_DEMO: `facility_attr22`, "Parent Facility", category NetworkModel).
  - `Filter` is a facility query that says which facilities are of that definition; the origin must satisfy it.
  - Path tokens seen in the IL: `%PARENT%`, `:` as step separator, otherwise a step name matched with the definition's `OrderInTypeAttribute` (case-insensitive equality), for example `%PARENT%:OilMeter`.
- `ResolveRelativeFacility(origin, relation, facClient)` finds the definition the origin matches, then the path for `relation`, and walks the parent link attribute. Results are cached per origin and relation.
- ForeSite loads the definitions from a CygNet **settings package file** (`CygNet.Internal.SettingsPackage(path, StorageType.BSS)`, setting `RelativeFacilityContent`).
  The path comes from the ForeSite system setting "Relative Facility Mapping Schemes". The CygNet API can also load them from the domain: `RelativeFacilityDefinitionSets.LoadFromDomain(domain)`; this is read-only.
- **CYG_DEMO:** `LoadFromDomain(27212)` returns an empty set (`DefaultSet=""`, XML `<RelativeFacilityDefinitionSets DefaultSet="" />`). Available services are CYG4T.FAC, CYG_DEMO.FAC, WAOIL.FAC. So **no relation names exist on CYG_DEMO's domain store**. A file-based package, if one exists for ForeSite, was not found and was not searched for.

## 2. Relations on CYG_DEMO and what they resolve to

None are defined in the domain, so nothing resolves. I tried synthetic in-memory definitions (Well, GasMeter, OilMeter with
`%PARENT%` and child paths, filter and `OrderInTypeAttribute` variants, associated service set). Every `ResolveRelativeFacility` call returned null, even the trivial child-to-parent hop.
I did not find out why (IL shows the resolver needs the filter list from its own `_facClient`, which is probably only set by the
2-arg overload path; unverified). **Treat live resolution through the CygNet API as unproven.**

## 3. Hierarchy from facility attributes (live, read-only)

CYG_DEMO.UIS has 2063 facilities (types: WELL/REMDEV 1060, GENFAC 511, WELL/DDSFAC 97, WELL/GENFAC 23, REMDEV 65, SOCKET 45, BLOCKVALVE 105, CHOKE 41, COMMDEV 20, meters, tanks, and so on).
In-use attribute columns: `facility_info0` Location, `facility_info1` Contact, `facility_attr7` COMM Device SM (2 filled), `facility_attr8` Link Facility SM (1 filled), `facility_attr22` Parent Facility (197 filled).

- Parent links (attr22): 197, all depth 1, none dangling. NETWMODEL parents 176+17 valves, chokes, sinks and sockets (NETWORKMODEL1/2, roots); WELL parents METER/MTRRUN children (`GLWELL_00001` has `GASMETER_01` and `OILMETER_01`; `GLWELL_00005` likewise; 2 MTRRUN, 2 MTRRUNO).
- The RPOC wells (`RPOC_00001` and the other ~1000) have **no parent and no children**. `GetLinkedDevices(RPOC_00001)` returns only itself. So for the demo data the hierarchy field > route > well > devices **cannot be built from facility attributes**; only a 1-level well > meter and network model > equipment structure exists.
- Field/route are not facility attributes here; they would have to come from naming, `facility_info0`, or a ForeSite-side hierarchy.

## 4. ForeSite RelativeFacilityMapping

- Model (`POP.Settings\RelativeFacilityMapping.cs`): `RelativeFacilityMapping { Id (Guid), Name, WellType, Quantities[{WellQuantity, Relation}], AdditionalUDCs[{UDC, Name, Relation}], Commands[{WellCommand, Relation}], SetPointInfo }`.
- Storage: there is **no database table** for mappings. They are serialized (DataContractSerializer, `RelativeFacilityConfiguration { Files[{Path,IsDefault}], Mappings[] }`) into the ForeSite system setting `Relative Facility Mapping Schemes` (`SettingServiceStringConstants.RELATIVE_FACILITY_MAPPING_SCHEMES`). The only database trace is the nullable `Well.welRelativeFacilityMapping` Guid (migration `201907182359505_WellSensitivity_welRelativeFacilityMapping_NullableAssetBridge`); wells are cleared when a mapping is removed.
- Use: `CygNetWellManager.GetRelativeFacilityPointTag` re-points a point tag for a quantity (or optional UDC) to the facility returned by the relation; no mapping or empty relation keeps the well facility. Fixtures: `Testing\Integration Tests\POPServer.IntegrationTests\TestDocuments\GLRelativeFacilityMapping*.xml` (all relations null in the sample).

## Hierarchy options

1. **Parent Facility attribute (attr22)** as a generic parent link: works today on CYG_DEMO for meters and network models; zero effort, shallow.
2. **CygNet definition set** (domain store or package file): authoritative where a site has defined relations; empty on CYG_DEMO.
3. **Adapter-owned relationMap** (quantity or UDC to a simple relation expression such as `Parent`, `Child:<TYPE>`) evaluated by the adapter over attr22, independent of CygNet's definition store, with import of ForeSite mappings as a later step.

## Recommendation

Implement option 3 first (opt-in, per connection, `relationMap: Quantity -> relation`, default off so behaviour is unchanged), resolving over attr22 with
a cache, and surface related facilities as hierarchy hints in discovery (parent id, child ids). Add option 2 only for a site that actually has definitions, after the null-resolution question below is settled. Do not rely on RPOC wells having relatives.
