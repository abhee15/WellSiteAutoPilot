# Module Authoring — section-by-section UX review gates

Status: living review checklist · 2026-11-16 · use with [data-flow workbench design](module-authoring-data-flow-ux.md).  
This is a design-quality review, **not** a claim of implemented complex authoring or licensed provider testing.

## Product rule

**Keep the current engineering task obvious.** The workbench must answer: *What am I editing? What does it consume? What does it produce? What happened in the last test?* At each increment we check the real page and revise existing controls before adding new panels. Use complex scenarios (structured surface cards; card calibration with arrays, a calibration record and two differently typed outputs; independent ForeSite/model/WAMI roles), never only a single threshold.

Research principles: [NN/g progressive disclosure](https://www.nngroup.com/articles/progressive-disclosure/) says the first view must contain frequent actions, while advanced settings should be plainly discoverable; [NN/g complex application design](https://www.nngroup.com/articles/complex-application-design/) recommends flexible workflows, reducing clutter without reducing capability, and preserving context across tools. These recommendations guide our decisions, not literal components to copy.

## Decision gate for every new authoring capability

1. **Find the real contract**: POC/runtime/provider simulator examples, types, units, quality/time requirements, execution authority and failure semantics. Record what is unverified.
2. **Inspect the actual UI first**: screenshots at desktop/laptop/iPad, current visible hierarchy, information lost or repeated and available space.
3. **Check reuse**: existing page/header/fields/tabs/status/notice primitives and tokens before adding a bespoke widget. No duplicate navigation, fake data flow or extra persisted UI model.
4. **Use the least complex useful affordance**: inline selected-step detail before a multi-column inspector; a focused dependency projection before a canvas; one disclosure level before accordion nesting. Keep important errors in view.
5. **Verify behavior**: tests for selection, stale async state, unsaved changes, compatibility, typed schema, keyboard focus, narrow widths and authority boundaries. Real browser screenshots plus CI; simulator outcomes are *not* licensed provider acceptance.
6. **Only then increase complexity**: one reviewed operation or capability at a time, with a visible difference that makes the current task simpler.

Unresolved: general complex calculation authoring, arbitrary Python/.NET code introspection, WAMI multi-role production runtime and licensed ForeSite/CygNet validation are beyond the current editor. **Do not turn design examples into execution claims.**
